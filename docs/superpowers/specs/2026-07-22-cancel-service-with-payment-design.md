# Cancel Service with Payment Handling

**Date**: 2026-07-22
**Status**: Approved

## Problem

Currently, cancelling a service only transitions the status to `CANCELLED` and optionally returns spareparts to stock. It does **not** handle existing payments — if a service has been paid (full or partial) and is then cancelled, the payments remain in `COMPLETED` status with no financial reversal.

Additionally:
- The Cancel button is shown unconditionally for all non-cancelled statuses, ignoring domain `canCancelService()` checks
- The Cancel Dialog (Radix Dialog, `z-50`) inside the Service Detail Sheet (Radix Sheet, `z-50`) can close both when clicking outside the dialog due to z-index stacking conflicts
- The Escape key handler in `ServiceDetailContent` doesn't stop propagation when `activeTab === "general"`, causing Escape to close both the dialog and the parent Sheet

## Scope

1. Allow cancel at `SELESAI` status for `MASTER_ADMIN` and `ADMIN` roles
2. When cancelling a service that has payments, offer a choice of **Refund** (return money to customer) or **Void** (cancel internally without returning money)
3. Both RPCs (`void_service_payment`, `refund_service_payment`) exist in the database but are not wired to the UI — wire them
4. Fix Cancel button gating using domain `canCancelService()`
5. Fix z-index/click propagation issue between Dialog and Sheet
6. Fix Escape handler to not close the Sheet when a dialog is open

## Non-Goals

- Cancellation at `SELESAI` without payments remains prohibited (must reopen first)
- Per-payment-method void/refund choice — single toggle applies to all payments
- No separate notification flow for cancel+refund (existing `SERVICE_CANCELLED` audit log suffices)

## Design

### 1. Domain Changes (`src/domain/service/service-workflow.ts`)

Add `"SELESAI"` to `CANCELLABLE_STATUSES`:

```typescript
const CANCELLABLE_STATUSES: ServiceWorkflowStatus[] = [
  "MASUK",
  "DIAGNOSA",
  "PERBAIKAN",
  "QC",
  "SELESAI",
];
```

Update `ROLE_RULES` for `SELESAI`:

```typescript
SELESAI: {
  allowedNext: [],
  canCancel: true,   // was false
  canReopen: true,
},
// FRONTLINER and TECHNICIAN remain canCancel: false
```

Update `validateCancelService`: change the terminal-status rejection message from a hard block to a payment-aware prompt.

### 2. Cancel Service Dialog (`src/components/services/cancel-service-dialog.tsx`)

**Props changes:**
- Add `payments?: ServicePaymentRecord[]` (payment records for the service)
- Add `brandSlug: string` (was only passed to server action, now needed for display)

**UI changes:**
- When `service.status === "selesai" && payments.length > 0`:
  - Show a section titled "Pengembalian Pembayaran"
  - Display total payment amount to be reversed
  - Toggle: **Refund** (default) / **Void** with description:
    - Refund: "Dana dikembalikan ke pelanggan"
    - Void: "Transaksi dibatalkan tanpa pengembalian dana"
- Existing reason textarea and return-stock checkbox remain unchanged
- Submit button calls `cancelServiceAction` with new `paymentAction` field

**State:**
```typescript
const [paymentAction, setPaymentAction] = useState<"refund" | "void">("refund");
```

### 3. Server Action (`src/server/actions/service-workflow.actions.ts`)

**`cancelServiceAction` input changes:**
```typescript
interface CancelServiceInput {
  brandSlug: string;
  serviceId: string;
  reason: string;
  returnStock: boolean;
  paymentAction?: "void" | "refund";   // new
}
```

**Flow changes** (after status transition to CANCELLED):
1. Return spareparts to stock (existing, if `returnStock === true`)
2. If `paymentAction` is set:
   - Load service's completed payments via `getServicePayments(serviceId)` filtered to `payment_status === "COMPLETED"`
   - For each payment, call the appropriate RPC:
     - `void_service_payment(p_service_payment_id, p_reason, p_created_by)`
     - `refund_service_payment(p_service_payment_id, p_reason, p_created_by)`
   - Idempotency keys auto-generated by RPC prevent double-reversal
3. Audit log entry remains `SERVICE_CANCELLED` (payment RPCs write their own audit entries)

**Validation:**
- If `paymentAction` is set but no COMPLETED payments exist, proceed without reversal (no-op)
- If `paymentAction` is set but service is not at SELESAI, ignore `paymentAction` (MASUK–QC statuses don't trigger payment handling)

### 4. Service Detail Content (`src/components/services/service-detail-content.tsx`)

**Cancel button gating:**
- Import `canCancelService` and `normalizeServiceStatus` from domain
- Import `ServiceWorkflowRole` type
- Use `canCancelService({ currentStatus, role })` to gate Cancel button visibility

```typescript
const workflowStatus = normalizeServiceStatus(localStatus);
const userRole = (role?.toUpperCase() ?? "MASTER_ADMIN") as ServiceWorkflowRole;
const canCancel = canCancelService({ currentStatus: workflowStatus, role: userRole });
```

Cancel button: `{!isCancelled && canCancel && (...)}`

**Payment data to dialog:**
- Pass `payments` (enriched payments from `enrichedPayments` or `service.payments`) and `role` to `CancelServiceDialog`
- Filter to only `COMPLETED` payments and calculate total

**Escape handler fix** (already applied in commit):
```typescript
if (cancelOpen || paymentOpen) return;  // don't intercept Escape when dialog is open
// always stopPropagation on general tab
```

### 5. z-index Fix

**Problem**: Both Sheet overlay and Dialog overlay use `z-50`. Clicking outside the Dialog content but inside the Dialog overlay can trigger the Sheet overlay's close handler.

**Fix**: In `ServiceDetailSheet`, when a modal dialog is open inside the content, prevent the Sheet overlay from closing. This can be done by:
- Adding `onInteractOutside={(e) => { if (cancelOpen || paymentOpen) e.preventDefault(); }}` to the Sheet (not always possible in all Sheet implementations)
- OR better: wrapping the content in a container that captures pointer events when dialogs are open

Simplest fix: Disable the Sheet overlay close behavior when any modal is open inside. The Sheet already uses `onOpenChange` — we can't prevent individual interactions there. Instead, the most reliable fix is to ensure the Dialog has a higher z-index than the Sheet when both are open.

**Implementation**: Override the Dialog's z-index when rendered inside the Sheet:
```tsx
// In CancelServiceDialog, add z-[60] to overlay
// Or detect portal stacking order
```

Given that both use `z-50` and Radix typically appends new portals to the end of `<body>`, the Dialog should naturally stack above the Sheet. If the issue persists, the fallback is to use CSS class overrides.

### 6. Payment Data Flow

- `ServiceDetailSheet` already receives `role` and passes it to `ServiceDetailContent`
- `ServiceDetailContent` has `enrichedPayments` derived from `service` data
- Pass `enrichedPayments.filter(p => p.paymentStatus === "COMPLETED")` to `CancelServiceDialog`

## Database RPCs (already exist, no changes needed)

Both RPCs handle idempotency, financial ledger reversal, and payment status update:

| RPC | Payment Status | Reversal Type | When to Use |
|-----|---------------|---------------|-------------|
| `void_service_payment` | `VOIDED` | `VOID` | Internal cancellation, no money returned |
| `refund_service_payment` | `REFUNDED` | `REFUND` | Money returned to customer |

## Testing

1. Cancel MASUK status — no payment section shown, existing behavior preserved
2. Cancel SELESAI + UNPAID — domain validation rejects (must reopen first)
3. Cancel SELESAI + PAID — dialog shows payment section with Refund default
4. Cancel SELESAI + PAID + Refund — payments marked REFUNDED, account movements created
5. Cancel SELESAI + PAID + Void — payments marked VOIDED, account movements created
6. Cancel SELESAI + PARTIAL — remaining balance cancelled, paid portion refunded/voided
7. Double-click submit — idempotency keys prevent double reversal
8. Escape key — closes Cancel dialog, does NOT close Sheet
9. Click outside Cancel dialog — closes Cancel dialog, does NOT close Sheet
